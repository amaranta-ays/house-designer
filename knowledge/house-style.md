# House Style — Cross-Medium Aesthetic Specification

**Revision:** 2026-11-06 · **Version:** 1.12.0

## Aesthetic Statement

Modern Tech minimalism with editorial sophistication. Geometric sans throughout (Inter), restrained weight usage (400/500 default), one rich-but-muted accent (Teal 900 #134E4A), warm-white paper for documents and stark white for screens, italic emphasis only (no serif fork). Hierarchy is carried by size, color, space, and tracking — not by weight contrast.

## The Won't-Do List (Forbidden Patterns)

Expanded with examples in [`../../agents/house-designer/references/anti-patterns.md`](../../agents/house-designer/references/anti-patterns.md).

- Gradients of any kind (`linear-gradient`, `radial-gradient`, `conic-gradient`)
- Multiple accent colors in the same artifact
- Pure black `#000000` text (use `#0A0A0A` on warm white, `#0A0A0A` on stark white)
- Bold weights (600/700) without explicit user opt-in
- Serif typefaces anywhere (the system has rejected the editorial fork)
- Emoji glyphs as visual elements
- Generic SaaS template tropes — purple hero gradients, "trusted by" logo strips, three-feature-card-with-icon grids, pastel pill backgrounds
- Box shadows beyond a single subtle layer (max: `0 1px 2px rgba(0,0,0,0.04)`)
- Border radii > 12px
- Parallax, bouncy springs, attention-seeking motion
- Text-only async indicators (`"Refreshing…"`, `"Loading…"`) without an accompanying `<OrbitSpinner />` — see [`motion.md`](motion.md#mandatory-placement-approved-2026-06-04)
- Third-party spinner components (MUI `CircularProgress`, Bootstrap `.spinner-border`, generic `animate-spin` SVGs, etc.) — only the canonical orbit spinner from `house-style-render-ts` is permitted
- Stand-in spinners in mockups and previews (a CSS-rotated ring, a generic spinning icon, an animated ellipsis) — mockups show the canonical orbit, inlined from `orbit-spinner.svg`; see [`motion.md`](motion.md#the-main-spinner-in-every-medium-mockups-included-approved-2026-10-25)

## Locked Aesthetic Decisions (Source: 2026-05-10 brainstorming session)

1. **Primary type family:** Inter. Default weights 400/500. Weights 600/700 reserved for explicit user request. No emoji in body content. (One medium departs: `.docx` output from `house-style-render` is set in Calibri, because a DOCX names fonts rather than carrying them — see the DOCX body-font divergence in [`type-stack.md`](type-stack.md#docx-body-font-divergence-decided-2026-09-09).)
2. **Single accent color:** Teal 900 `#134E4A`. Single-accent rule. Never as a background fill. (See carve-outs #5 and #9.)
3. **Background by surface:** Documents/print → warm white `#FAFAF8`. GUI/screens → stark white `#FFFFFF`.
4. **Emphasis treatment:** Inter italic for chat (.medium-gui), email (.medium-email), and slide (.medium-slide) mediums. Inter bold (weight 700) for document (.medium-document) mediums — briefings, memos, status briefs, one-pagers — per the v1.4.0 carve-out approved 2026-05-13. The italic-only rule held for literary prose; status briefs and operational documents are scanned more than read and need heavier emphasis to surface load-bearing facts at body size. Accent color (`#134E4A`) applies in both treatments. No serif typefaces anywhere.
5. **Slide-emphasis carve-out (approved 2026-05-12; surface changed 2026-09-05):** Slide / HTML-presentation surfaces may use cyan-blue emphasis (`#0A1F2A`) with the bright accent (`#4195BE`). This is no longer a single-accent-*family* rule: the pair is a different hue from `#134E4A`, and the emphasis surface is the one place a second hue is permitted. Restricted exclusively to slide / HTML-presentation surfaces; GUI dashboards, documents, email, and print remain on the canonical light surfaces. See [`color.md`](color.md) for the surface rules table and class application.
6. **Surface-hierarchy color inheritance (approved 2026-05-13, MUST-implement 2026-05-13):** Primary surfaces (top-level panels/sections) are theme authorities — each MUST declare the five canonical chrome slots (`--surface-chrome-bg`, `--surface-chrome-fg`, `--surface-chrome-fg-secondary`, `--surface-chrome-button-bg`, `--surface-chrome-button-border`) on its root, wrapped in a DOM element (not a fragment) so child modals/drawers/popovers are DOM descendants. Secondary surfaces MUST read chrome from those variables via CSS cascade — never from color literals — and MUST use the canonical `.hsr-chrome-button` / `.hsr-chrome-icon-button` classes for any button rendered on chrome. Independent surfaces (global modals, system notifications) and semantic-color overrides (destructive, error, success) are explicit exceptions. See [`color.md`](color.md#surface-hierarchy-color-inheritance-approved-2026-05-13) for slot definitions, scope, examples, the canonical chrome-button classes, and the required implementation pattern.
7. **Canonical chip primitives (approved 2026-05-13, MUST-implement 2026-05-13):** Categorical chips (phase, type, complexity, tag, account, status) MUST use the canonical `.hsr-chip` primitive with state variants — `default` (neutral outlined), `is-current` (accent outlined, one-per-scope), `is-done` (muted dashed), `is-success` / `is-danger` / `is-warning` (semantic carve-outs). Pastel-pill recipes (`bg-{hue}-100 text-{hue}-700`) and per-category color maps (e.g. `PHASE_COLORS`, `COMPLEXITY_COLORS`) are anti-patterns — they regress to multi-hue categorical hierarchy that the single-accent rule rejects. Hierarchy belongs to state and copy; hue is reserved for the accent role and the three semantic carve-outs. Chip variants read from `--chip-*` tokens (defaults in [`tokens.css`](../../plugins/house-style-render/shared/tokens.css)); surface themes override those tokens on dark chrome to flip polarity automatically. Three companion primitives (`.hsr-mono-id`, `.hsr-label`, `.hsr-status-italic`) cover identifier / iteration-counter / transient-status roles that aren't chips. See [`color.md`](color.md#chip-primitives-approved-2026-05-13) for the full primitive catalog, polarity behavior, and migration notes. (See carve-out #9 for the one filled exception, scoped to printed output from the PDF and DOCX adapters.)
8. **Mandatory orbit spinner for async work (approved 2026-06-04, MUST-implement 2026-06-04):** Any user-initiated async operation that takes longer than ~250ms and visibly delays the user's next action MUST surface the canonical `<OrbitSpinner />` (from `house-style-render-ts`) inline, paired with a textual state label transition (e.g., `"Refresh now"` → `"Refreshing…"`). The 2026-05-13 carve-out in [`motion.md`](motion.md#functional-async-state-carve-out-approved-2026-05-13) is hereby strengthened from permission to obligation. Forbidden alternatives: text-only loading indicators, animated-text tricks (bouncing periods, marquee ellipses), and any non-canonical spinner library or framework default. See [`motion.md`](motion.md#mandatory-placement-approved-2026-06-04) for the placement table per context (buttons, inputs, modals, data loaders) and the 250ms duration heuristic. **Amended 2026-10-25 (v1.11.0):** the orbit is the main spinner in every medium *and at every design stage* — mockups and previews shown for sign-off use the canonical orbit (inline the symbol from `orbit-spinner.svg` in self-contained HTML), never a stand-in ring or generic spinning icon; see [`motion.md`](motion.md#the-main-spinner-in-every-medium-mockups-included-approved-2026-10-25). **Amended 2026-11-06 (v1.12.0):** an orbit beside a label shares the label's colour (white on dark chrome) and the label is upright, never italic, with no leading dot; see [`motion.md`](motion.md#orbit-with-a-label-one-colour-upright-approved-2026-11-06).

9. **Print time-gutter badge carve-out (approved 2026-09-09):** The **printed day sheet** may set a timestamp as a filled accent badge — white text on Teal 900 `#134E4A`, fill hugging the timestamp only. This is a narrow exception to two standing rules: the accent "never as background fill" (decision #2, [`color.md`](color.md)) and "chips are outlined, not filled, on the canonical light surface" (decision #7). Rationale: a day sheet is read standing on a platform, at a glance, at 8pt; the times are its spine, and an outlined chip at that size reads as noise rather than structure. **Scoped to printed documents rendered by `house-style-render`'s PDF and DOCX adapters** — GUI dashboards, email and slides keep outlined chips, and nothing in the web or React layer inherits this. Implemented as `code_fill` in [`adapters/pdf.py`](../../plugins/house-style-render/py/house_style_render/adapters/pdf.py) and its DOCX sibling. A badge is never painted behind a blank span: the travel day sheet puts a non-breaking space in the gutter for an item with no recorded time, and a fill would turn that deliberate blank into a visible empty chip.

**Amended 2026-09-09 (v1.8.0).** As first written this carve-out said "scoped to the PDF day-sheet time gutter and nothing else", and that `code_fill` was `None` by default "so no other consumer inherits it". Both halves are now out of date: the day-sheet profile was promoted to those adapters' default, so `code_fill` is the accent unless a caller opts out with `PdfOptions.memo()`. The scope is unchanged in substance — the badge still reaches only printed output from these two adapters, and they still have exactly one consumer — but the *mechanism* is now opt-out rather than opt-in, and the sentence describing it had to change with it.

10. **Deck cover, footer and rhythm (approved 2026-10-23):** Decks open with a footer-less `title` slide. Every other slide's footer is client · brand mark · page number, all in the mid grey `--color-fg-tertiary`. The brand mark is opt-in per deck, tagline-free and single-colour. Space under the headline rule equals the space over it, measured in glyph ink. Every bullet list is spaced 1.2cqw between items. Compare column titles stand 1.6cqw clear of their bullets. See [`density.md`](density.md#deck-cover-footer-and-rhythm-amendment-approved-2026-10-23).

Required implementation: primary surfaces declare the slots on their root; child surfaces consume them via CSS cascade; color literals in child surfaces are an anti-pattern that fails review. - **1.3.2 (2026-05-13):** Added canonical chrome-button classes to `components.css` — `.hsr-chrome-button` (solid-ish pill button with bg + border) and `.hsr-chrome-icon-button` (transparent icon-only button). Both read from the five chrome slots and implement default, hover, focus-visible, and disabled states via `color-mix()` against `--surface-chrome-fg`, so hover behavior is consistent across any theme polarity (light-on-dark, dark-on-light). Chrome buttons MUST use these classes; re-implementing hover math in consumers is now an anti-pattern. Also documented the fragment-vs-div constraint discovered when implementing the rule in NCC — primary-surface render root must be a DOM element, not a fragment, so sibling-rendered child surfaces are DOM descendants and inherit via cascade.
- **1.4.0 (2026-05-13):** Document-medium emphasis carve-out. Italic remains the canonical treatment for chat/email/slide mediums. Rationale: operational documents are scanned for load-bearing facts (dates, owners, status counts); at 12px body size italic is subtle to the point of being missed, while bold draws the scan-eye reliably. Decided via A/B preview on a client status brief; user picked the bold variant. Consumers rendering document-medium content MUST load Inter weight 700 in addition to 400/500. See [`type-stack.md`](type-stack.md#emphasis) for the per-medium emphasis table and the updated weight usage rule.

Added 14 chip tokens to `tokens.css` (`--chip-*` family) with light-surface defaults; surface-theme classes override these to flip polarity automatically on dark chrome. Forbids `bg-{hue}-100 text-{hue}-700` pastel-pill recipes and per-category color maps. The day-sheet profile — 8pt body at print leading, 16/10/10 accent headings, tracked uppercase section titles, white-on-teal time badges, two columns — was promoted to the default of `house-style-render`'s PDF and DOCX adapters. `code_fill` and `code_bold` are therefore on unless a caller asks for `PdfOptions.memo()` / `DocxOptions.memo()`, which hold the pre-2026-09-09 settings (11pt body, 24/18/14 near-black headings, no badge, no bold). The promotion was checked against every project that imports the package first: NCC does not reference it at all, the portfolio app uses four colour tokens and the `shared/` directory, deck-studio uses `tokens.json`; none of them touch these adapters, so no existing document changes appearance. **Superseded the same day by 1.9.0:** the portfolio app moved both its exports onto these adapters hours later, so it is now their second consumer and that sentence no longer describes the blast radius.
- **1.9.0 (2026-09-09):** Amended decision #1 — `house-style-render`'s **DOCX adapter now sets body text in Calibri**, not Inter. The PDF adapter is unchanged and stays on Inter. A PDF embeds a subset of the font it is handed; a `.docx` only names one, and Word resolves that name on whichever machine opens the file. Inter ships with no operating system — on the machine this was built against it was installed per-user only, i.e. present for its author and absent for every recipient — while Calibri ships with every Office install. This is the same reasoning already recorded for the mono face (Courier New over JetBrains Mono, v1.7.0 era), applied to the body face; the adapter had been stating that rule in its own module docstring and then not following it for the body font. Both consumers had already overridden the default by hand — the portfolio app on migrating, the travel app immediately after — which is what a wrong default looks like from outside. Relying on fallbacks instead was tried and is recorded as insufficient: Word 16.0.20026 rendered Times New Roman for a missing font despite `w:altName`, a patched theme `minorFont`, and `w:rFonts` at run and style level (measured 2026-05-11). Those three hardening steps moved from the portfolio app's export module into the adapter on this date so every consumer gets them, but they are defence in depth — the font name is what decides the outcome. Cost: a `.docx` and a `.pdf` of the same document are in different faces, with identical sizes, colour, spacing and layout. See [`type-stack.md`](type-stack.md#docx-body-font-divergence-decided-2026-09-09).
